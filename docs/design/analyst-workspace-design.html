1. Summary

The application is a self-hosted security operations workspace for teams that use Microsoft Defender XDR and Microsoft Sentinel. Analysts keep a watch list of vendors, products, CVEs and tags; a worker matches it hourly against two public threat-intelligence feeds; analysts open hunt cases, review and approve read-only KQL searches, inspect stored result samples, and propose containment actions that an approver dry-runs and decides. A set of AI agents can read intelligence, hunts and memory and can propose searches or actions. They cannot run or approve anything.

Three design rules shape almost every component:

  1. People approve; machines propose. No code path lets an agent execute KQL or a response action. Live execution is off by default and needs two independent switches.
  2. Every query is tenant-scoped on the server. All organisation data is filtered by org_id in server code; UI hiding is never the control.
  3. Untrusted input stays data. Feed content, model output, query results and webhook targets are validated, escaped or allowlisted before use.

4. Data flows

4.1 Intelligence ingest and matching (W1)

  1. The worker (server/cli/worker.ts) runs an ingest cycle at start and every hour: fetchAndIngestPwnWatch (incidents, changes, tags) and fetchAndIngestKev, via politeFetch in server/ti/http.ts (cache table ti_fetch_cache, TTL at least 3600 s by default).
  2. Records are parsed with zod schemas; invalid items are skipped and counted, not stored.
  3. server/ti/matcher.ts matches each org's active watches (keyword and vendor are case-insensitive whole-word, at least 3 characters; CVE and tag are exact) and writes watch_hits rows with org_id.
  4. Five minutes after local midnight in APP_TIMEZONE, the worker builds the previous day's digest per org and emails owners when SMTP is configured (server/ti/digest.ts). Day bounds are DST-safe, including zones with no local midnight.

4.2 Search approval and execution (W2)

  1. An agent tool (propose_kql) or an analyst creates a kql_proposals row (status proposed, expiry set).
  2. A person reviews and may edit the KQL, then approves. approveAndRunKql (server/hunting/hunts.ts) is the only code path that executes KQL and requires a human user id.
  3. assertSafeKql rejects external data, HTTP, plugin, cross-cluster and management commands. The claim is atomic: only one approver moves proposed to approved.
  4. The hunting client obtains a client-credentials token for the org's read-only app (server/hunting/broker.ts), checks the request against HUNTING_ALLOWLIST, applies row and timeout caps, and stores a summary (row count, columns, a sample of at most 20 rows) plus an evidence event. In demo mode, labelled fixture rows are returned instead.

4.3 Response (W4)

  1. A proposal (response_proposals) holds targets, a blast-radius summary and payload. Agents may create proposals only through propose_response, on behalf of a member.
  2. An approver dry-runs it: executors compute the exact calls and any blockers without sending anything.
  3. A different approver approves (self-approval is refused unless RESPONSE_ALLOW_SELF_APPROVAL=true).
  4. Execution happens only if RESPONSE_DRY_RUN=false and the executor flag for that action type is on. Calls are checked against RESPONSE_ALLOWLIST, capped by RESPONSE_MAX_LIVE_TARGETS, and recorded per call. Rollback is a new proposal through the same gates.

4.4 Chat (W6)

  1. POST /api/chat (server/chat/handler.ts) authenticates, rate-limits per IP, loads the thread for that user and org, appends the user message and builds history from the database (the client never supplies history).
  2. server/agents/runtime.ts builds the system prompt from the agent's charter plus org memory and runs the TanStack AI tool loop (at most 6 iterations; 4 for delegated specialists) with only that agent's tools.
  3. The model is Azure OpenAI via server/agents/model.ts, signed in with DefaultAzureCredential (managed identity). The response streams to the browser as Server-Sent Events and is persisted on completion; every turn and tool call writes an agent_decisions row.

8. Component and state catalogue

For each interactive component: what it does, keyboard support, accessibility, security notes and the states it must render. "Permission" means the control is absent or disabled for the role and the server refuses the action.

8.1 Result grid (ResultGrid)

  • Interaction: sortable columns (sort held in the URL and shared with the inspector); wrap toggle; click or Enter opens a row.
  • Keyboard: roving tab index; j/k or arrows move; Enter or Space opens; Escape closes the inspector.
  • Accessibility: native table, aria-sort, selected row marked with aria-selected and an inset bar (not colour alone); key hints visible.
  • Security: cells rendered as text; long values truncated with the full value in the inspector; nothing interpreted as HTML.
  • States: no sample stored; zero rows returned (stated as a result); filtered to nothing (with clear action); sample smaller than row count (notice: filters apply to the sample only); demo data tag on the search.

8.2 Row inspector (Inspector)

  • Interaction: Fields and Raw JSON views; hide empty fields; per-field Show only, Filter out, Copy, Add to new search; previous and next follow the visible order.
  • Keyboard: j/k step rows; Escape closes and returns focus to the row being shown.
  • Accessibility: side panel on wide screens; at 1180 px and below it is a role="dialog" with aria-modal, focus moves to its heading, Tab is contained and the rest of the page is inert.
  • Security: "Add to new search" drafts | where with kqlIdentifier (bracket-quoted names) and kqlLiteral (escapes quotes, backslashes, line breaks and control characters). The draft is a proposal: it still needs approval and passes assertSafeKql.
  • States: clipboard unavailable (message); empty values shown as "empty", never blank or zero.

8.3 Query review panel

  • Interaction: editable KQL with "edited from the proposal" indicator and restore; Approve and run, Reject; expiry shown.
  • Security: what is approved is exactly what runs and is stored; server enforces expiry, single claim, safety filter and caps.
  • States: needs review, running, ran, failed (error shown), rejected, expired (with "edit as new search"), demo mode notice.

8.4 Evidence timeline and entities

  • Timeline: filter chips (All, Searches, Results, Notes, Schedules) in the URL; entries link to the producing search or to a repeat run's own sample; actors labelled agent, person or system.
  • Entities: devices, accounts, files and network values counted within the sample only (stated); selecting one adds a filter.
  • States: nothing yet; no entity columns; sample without column metadata (columns inferred).

8.5 Approval decision panel

  • Permission: analysts see a read-only notice; approvers see Dry run, Approve, Reject and, when approved, Execute. Requesters see a notice that another approver must decide. The server enforces all of these.
  • States: pending, approved (executor off, dry-run, live), executed, failed or partial, rejected, expired; dry run with blockers ("would be refused"); per-call results matched by position; rollback proposed.

8.6 Chat

  • Interaction: Enter sends, Shift+Enter new line, Stop reply, Copy, rating; agent selector; suggested questions; draft survives reloads.
  • Accessibility: transcript is role="log"; one polite status per reply ("Intel replied"), not per token; tool steps are a labelled list with pending, done and failed states.
  • Security: markdown rendered with react-markdown and remark-gfm without raw HTML; external links open in a new tab with noopener noreferrer; no model credentials reach the browser.
  • States: model not configured (read-only, setup notice), thinking, streaming, stopped, model error with retry, empty conversation.

8.7 Control panel and feed status

  • Feed state per required endpoint: live, stale (older than 3 hours, written out), not fetched; the oldest endpoint decides.
  • Counts come from separate count queries; lists are capped previews. Waiting items exclude expired and already-approved items.
  • Hits-by-day chart: units, window, time zone and zero days are stated; consecutive calendar days are generated without DST errors.

8.8 Forms (settings, watches, notes, new hunt)

  • Visible labels; hints and errors linked with aria-describedby; errors announced (role="alert"); success announced politely; secrets in password inputs with autocomplete="new-password", never re-displayed.
  • Removing a watch, deleting a conversation and deleting a notification channel use an inline confirm step; focus moves to Confirm and returns to Delete on Cancel.

  • Result samples are small (at most 20 rows); filtering and sorting are client-side over the sample.

IMPLEMENTED KQL approval policy (KQL_APPROVAL_POLICY, rules in apps/web/src/shared/kql-approval.ts, shared by the server check and the UI notice). member (default, decided 08-11-2026): any member may approve and run a read-only search. approver: owners and approvers only. second-person: an approver other than the person who asked for the search (the proposer, or the chat user whose agent proposed it, stored as requested_by), and the query cannot be edited at approval; an edit becomes a new proposal.

10.2 Tenant isolation

  • Each org-owned table carries org_id; server functions take the org from the session, never from the request body.
  • Cross-references are re-checked in the same org (for example, a hunt's origin watch hit resolves only within the org; tested in test/workspace.test.ts).
  • Entra sign-in maps the token's tenant id to exactly one org; unknown tenants are refused before a user row is created and audited (sso_rejected_unknown_tenant).
  • Connector secrets use per-org env: reference prefixes; a reference outside the org's prefix is refused.
  • ASSUMPTION Isolation is enforced in application code. PostgreSQL row-level security is not used; a missing filter in new code would not be caught by the database.

12. Security controls in depth

12.1 Authentication, session, SSO and MFA

  • IMPLEMENTED Entra ID OIDC (openid profile email only), single tenant recommended; SAML per org (@better-auth/sso); email and password disabled in Azure (AUTH_EMAIL_PASSWORD=false).
  • ASSUMPTION MFA and phishing-resistant authentication are enforced by the identity provider (Conditional Access). The application does not implement its own second factor. Align the IdP policy with NIST SP 800-63B-4 at AAL2 or above, preferring phishing-resistant methods for owners and approvers.
  • IMPLEMENTED Sessions: idle timeout SESSION_IDLE_MINUTES (60) slides with activity; absolute cap SESSION_MAX_AGE_HOURS (12) since sign-in is enforced on every app request and in front of the auth endpoints; over-age sessions are revoked and audited (session_expired_absolute).
  • IMPLEMENTED Bootstrap: the first admin email is bound to the org; the first matching sign-in becomes owner.

12.2 Least privilege

  • Three separate Entra apps: SSO (sign-in only), hunting (ThreatHunting.Read.All, Log Analytics Reader, Sentinel Reader), response (Machine.Isolate, Sentinel Responder, Logic App Contributor on allowlisted playbooks). See docs/runbooks/entra-setup.md.
  • Deployment identity: GitHub OIDC federation to a Contributor role on the resource group only; no long-lived deploy secret.
  • Runtime identity: user-assigned managed identity with Key Vault Secrets User and Cognitive Services OpenAI User only.
  • Azure OpenAI resource with local (key) authentication disabled in the lab.

12.3 Secrets and key management

  • Azure Key Vault holds database-url, better-auth-secret, app-encryption-key, entra-client-secret; Container Apps resolve them with the managed identity.
  • Connector and webhook secrets are encrypted with AES-256-GCM under APP_ENCRYPTION_KEY (server/lib/crypto.ts, format v1.iv.tag.ciphertext).
  • IMPLEMENTED Key rotation: decryption also accepts APP_ENCRYPTION_KEY_PREVIOUS; pnpm rotate-secrets re-encrypts every stored secret under the current key in one transaction and reports counts only (docs/runbooks/key-rotation.md).

12.4 Transport and storage encryption

  • Ingress is HTTPS only; HSTS one year with subdomains. Database connections use sslmode=require.
  • ASSUMPTION Storage encryption at rest is provided by the platform (Azure Database for PostgreSQL and Key Vault defaults). No customer-managed keys are configured.

12.5 Input, query and injection protection

  • All server-function inputs are validated with zod; SQL is built with Drizzle (parameterised); ILIKE search terms escape %, _ and backslash.
  • KQL: human approval, assertSafeKql blocklist (external data, HTTP, Python and R plugins, SQL request, management commands, cross-cluster), length limit 10,000.
  • Generated KQL drafts escape literals and quote identifiers.

12.6 Untrusted intelligence ingestion

  • Fixed URLs, timeouts, bounded retries with back-off on 429 and 503, identifiable User-Agent, cache TTL at least one hour.
  • Schema-validated; invalid items skipped and counted; content stored and rendered as text; links open with noopener noreferrer.
  • IMPLEMENTED Feed responses larger than TI_MAX_RESPONSE_BYTES (25 MB) are refused, by Content-Length and while streaming, and nothing is cached.

12.7 Safe rendering of links, files and graphs

  • No graph rendering exists. Exports (hunt report Markdown, audit bundle JSON) are generated server-side and downloaded as files; the report redacts secrets and caps size (REPORT_MAX_CHARS).

12.8 Audit, redaction, privacy and retention

  • audit_events: sign-ins, rejections, role changes, connector and channel changes, response events, bootstrap, exports. agent_decisions: every agent turn and tool call, redacted.
  • Logs are JSON with request ids; authorisation headers, cookies, tokens and secrets are redacted.
  • Bootstrap audit stores no full email; people are shown by email only to members of the same org.
  • IMPLEMENTED Retention periods (section 6). GAP Deleting one person's data on request is a manual database task; there is no self-service export or erasure.

12.9 Supply chain and CI security

  • GitHub-hosted runners; actions pinned to commit SHAs; pnpm install --frozen-lockfile; lint, typecheck, tests, build and migration drift check on every PR.
  • Image job: build, SBOM (Anchore, SPDX), Trivy gate failing on fixable critical CVEs; image pushed to GHCR by immutable SHA tag.
  • Container runs as the node user with a health check.
  • IMPLEMENTED Dependabot (Actions, npm, Docker, weekly); CodeQL for TypeScript and workflow files on every PR, push and weekly; signed build provenance and SBOM attestations bound to the pushed digest; release tags are published only after both attestations succeed (docs/releasing.md).

15. Deployment and operations

15.1 Topology (Azure)

Bicep in infra/azure/: Container Apps environment with web (1 to 3 replicas, probes on /healthz and /readyz), worker (exactly 1) and a manual migration job; PostgreSQL Flexible Server (Burstable B1ms, 7-day backups); Key Vault (RBAC); Log Analytics and Application Insights; alert rules; user-assigned managed identity; optional Azure OpenAI role assignment. Docker Compose files support local and self-hosted use.

IMPLEMENTED privateNetworking=true (Bicep) puts the Container Apps environment and PostgreSQL in a VNet with a private DNS zone and public database access disabled. ASSUMPTION Not yet deployed anywhere; an existing environment cannot be switched in place. The lab still uses postgresPublicAccess=true ("Allow Azure services" firewall rule). Production should use private networking (VNet integration or a private endpoint) as described in docs/runbooks/azure-deploy.md.

15.2 Release and rollback

  1. Deploy workflow (manual dispatch on main): CI, image build with SBOM and CVE gate, then the production environment with required reviewers.
  2. Records the current revision, runs the migration job, rolls out web and worker, waits for the new revision, runs the smoke test.
  3. Rollback: re-point to the previous revision or image tag (docs/runbooks/rollback.md). Migrations are forward-only; schema changes must stay backward compatible for one release.

15.3 Backup and restore

Point-in-time restore of the database (7-day retention). A restore drill and recorded RPO/RTO are part of the go-live checklist (docs/go-live-checklist.md, docs/runbooks/backup-restore.md). PLANNED The drill has not been recorded for the lab.

16. Testing and acceptance criteria

16.1 Test inventory at the commit

  • Unit and integration (Vitest, real migrations on PGlite): 197 tests in 21 files; 195 pass and 2 are skipped (run locally on 8 November 2026); covers auth, RBAC, tenant isolation, hunting safety, schedules, response gates, notifications, TI, digests and time zones, agents and chat with a mock model.
  • End to end (Playwright, local, not in PR CI): golden path, hunt workspace (keyboard, filters, history, theme, 390 px and 1000 px dialogs), chat streaming (deterministic mock), axe scan.
  • End to end on a local production build of this branch (8 November 2026): all 6 Playwright specs pass with the nonce CSP active and no CSP violations, including the axe WCAG 2.2 AA scan.
  • Live lab check (8 November 2026): smoke test, in-container Azure OpenAI call via managed identity, Entra sign-in, hunt run, analyst read-only approval, streamed chat with a tool call.

16.2 Acceptance criteria

  1. An analyst cannot dry-run, approve, reject or execute a response proposal; the server returns an error even if the request is sent directly.
  2. A requester cannot approve their own proposal unless RESPONSE_ALLOW_SELF_APPROVAL=true.
  3. No agent tool can execute KQL or a response action; EXECUTION_TOOL_NAMES is empty.
  4. With default configuration, no response call leaves the application (dry-run on, executors off).
  5. A user in org A cannot read or change any org B record through any server function or API route.
  6. A KQL proposal containing a blocked operator is rejected before execution.
  7. Webhook URLs outside the allowed hosts, with credentials, a non-default port or HTTP are rejected.
  8. No secret value appears in logs, audit events, decision rows, memory entries or API responses.
  9. Feed, result and model text is never interpreted as HTML in the browser.
  10. Every view passes the axe scan for WCAG 2.2 AA in light and dark themes with 0 violations.
  11. All interactive features are usable with a keyboard alone; focus is visible and returns sensibly after dialogs close.
  12. Reload and browser back restore the hunt workspace view (search, row, filters, sort, timeline).
  13. Demo data is labelled at every place it appears; it is never presented as live.
  14. /readyz returns 503 until the database is reachable and migrations are current.
  15. The image build fails on a fixable critical vulnerability.
